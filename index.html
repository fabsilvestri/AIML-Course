The organising principle

Chapters never introduce themselves.

Every method enters this course at the moment an application breaks without it. You will not be shown regularisation and then given a problem for it. You will overfit something you built, measure it, and want the fix.

Each application spans two lectures.

A · Build

15 min — the problem, the data, the stakeholder.

15 min — choose a metric and commit to a target number, in writing, on paper.

60 min — build the simplest thing that runs. Everyone leaves with a number they are pleased with.

B · Break → Fix

20 min — the mathematical thread.

20 min — diagnose why that number was wrong.

35 min — the method that repairs it.

15 min — re-measure, and red-team a peer's notebook.

The number committed at the end of every Build lecture is what makes the following Fix lecture land: you predicted, you were wrong, and now you want to know why.

Working method

AI-assisted development. You will not type most of the code in this course — you will specify, read, test, debug and verify it.

#StepWho
1Specify — the input, the output, the constraint, the checkyou
2Generate — and then stop, before running anythingthe assistant
3Read — as a reviewer, not as an authoryou
4Test — against a case whose answer you already knowyou
5Verify — that the number means what it appears to meanyou

Steps 3–5 are the course. Step 2 is the part that is free.

Why the emphasis on verification

Machine learning fails silently. A bug in a training loop does not crash — it returns a plausible number:

  • A scaler fitted before the split leaks the test set into training. Great score, broken system.
  • A missing model.eval() leaves dropout active during evaluation.
  • A missing optimizer.zero_grad() accumulates gradients with no error.
  • A metric averaged per batch rather than over the set is wrong by construction.
  • Accuracy on an imbalanced set reports 90% for a model that predicts one class.

Every one of these runs. Every one produces a number. Each is diagnosed in a lecture, on code we wrote ourselves.

The notebooks are ours. The textbook supplies the syllabus, not the code. No notebook from the author, or from any other third party, is used in this course. Every notebook is written during the lecture, from a specification — and every lecture includes at least one worked assistant failure: an under-specified prompt, the plausible code it returns, the review question that catches it, and the corrected specification.

Four rules

  1. You may not submit code you cannot explain line by line. I will ask.
  2. Every number needs a baseline. A metric with nothing to compare it to is decoration.
  3. Every model needs an ablation. Remove a component; show the number moves.
  4. Report the failure cases. A system with no known failure mode has not been tested.

The twelve mathematical threads

Every Fix lecture opens with twenty minutes on exactly one mathematical object — the one the application you just built depends on. This is not a parallel theory course: each thread does visible work on a system you wrote.

  1. Least squares and the normal equation · Lecture 2
  2. Imbalance, and the non-monotonicity of precision · Lecture 4
  3. The bias–variance decomposition · Lecture 6
  4. Impurity, and variance reduction by averaging · Lecture 8
  5. SVD, PCA and Johnson–Lindenstrauss · Lecture 10
  6. Backpropagation as reverse-mode automatic differentiation · Lecture 12
  7. Variance propagation and weight initialisation · Lecture 14
  8. Weight sharing, equivariance and memory · Lecture 16
  9. IoU’s vanishing gradient; mAP · Lecture 18
  10. Stationarity, differencing and temporal leakage · Lecture 20
  11. Cross-entropy, softmax and logits · Lecture 22
  12. The contrastive objective and its temperature · Lecture 24
The threads are cross-referential and are meant to be taken in order. Thread 2 is used by thread 9; thread 1 is completed by thread 3; thread 5 returns in thread 12; thread 4 explains the ensemble variants used from Lecture 8 onward.

Assessment

ComponentWhat is assessed
Written examinationThe twelve mathematical threads: derive, state, apply
Red-team reportsFind the leakage or evaluation bug in another team’s notebook
Oral defence“Explain line 47. What breaks if I change this?”
Final projectOne application, iterated properly, with evidence

Note what is absent: there are no marks for a notebook that runs. Evidence earns marks.

Textbook and scope

Aurélien Géron, Hands-On Machine Learning with Scikit-Learn and PyTorch, O’Reilly, 2025 — Chapters 1–16. Every method, dataset and metric in this course comes from this book.

Scope discipline. If it is not in Chapters 1–16, it is not examinable. Where the field goes beyond the book, that will be stated explicitly in the lecture and then set aside.

Practicalities

  • Every lecture has a Colab notebook, linked from its own slides and from the list above.
  • Part I runs on a free CPU runtime. Parts II–IV need a GPU runtime.
  • Slides double as PDF handouts — append ?print-pdf to a deck’s URL and print to PDF.
  • In a deck: M opens the menu, S opens the speaker notes, C toggles the chalkboard, F goes full screen.
  • Lectures refer to one another relatively — in the next lecture, in two lectures — so the material does not depend on the timetable.
