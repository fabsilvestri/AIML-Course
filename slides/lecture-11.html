The setting: a catalogue nobody labelled

A marketplace holds millions of product photographs uploaded by sellers. The category field is free text, often empty, sometimes wrong. Two things the product team wants from the photographs alone:

  • Similar items — given one garment, the ten most like it, in milliseconds, across the whole catalogue
  • Groups — a first structure for a catalogue that has none

Every method so far needed a label per row. None of these questions comes with one. The network of today learns from the inputs by trying to reproduce them.

The labels are loaded, and used for exactly one thing Scoring. Nothing is fitted on them. Precision at ten and the clusters’ purity both read the labels after the fact, to say whether a representation learned without them means anything.

An autoencoder: compress, then reconstruct

The target is the input. The network is trained to return what it was given, through a code too small to hold it — so it has to learn what the images have in common.

The objective

  • The encoder turns 784 pixels into $d$ numbers — the code
  • The decoder turns the $d$ numbers back into 784 pixels — the reconstruction
  • The loss is the mean squared difference between the input’s pixels and the reconstruction’s: the loss of least squares, with the input standing in for the label
  • Trained by the five-line loop of Lecture 8; nothing in the loop knows there is no label

The whole design question is what stops the network from learning the identity.

Why a bottleneck: a constraint on what the network can reach

A regulariser — dropout, a penalty on the weights, randomly altered inputs — works by shrinking the set of functions the network can reach, so that fitting the training data no longer means memorising it. An autoencoder needs the same thing, for a sharper reason: with $d = n$ the identity is reachable, the loss is zero, and nothing was learned.

$d \ll n$copying: 784 numbers cannot pass through 32undercomplete

The undercomplete autoencoder, in PyTorch

class AutoEncoder(nn.Module):
    def __init__(self, d, hidden=256):
        super().__init__()
        self.enc = nn.Sequential(nn.Linear(784, hidden), nn.ReLU(),
                                 nn.Linear(hidden, d))
        self.dec = nn.Sequential(nn.Linear(d, hidden), nn.ReLU(),
                                 nn.Linear(hidden, 784), nn.Sigmoid())

    def forward(self, x):
        return self.dec(self.enc(x))
  • $784 \to 256 \to d \to 256 \to 784$; a sigmoid on the output, because a reconstruction is an image in $[0, 1]$
  • enc and dec are attributes on purpose: the code is read by calling the encoder alone
  • At $d = 32$: 419,120 parameters — the two 784-wide layers are almost all of them

The loop is the one you already own

for epoch in range(EPOCHS):
    net.train()
    for xb in batches(X_fit):          # no labels in the loader
        opt.zero_grad()                # 1
        out  = net(xb)                 # 2
        loss = F.mse_loss(out, xb)     # 3  the target is the input
        loss.backward()                # 4
        opt.step()                     # 5

One change from Lecture 8: the line marked # 3 compares the output with the input, where Lecture 8 compared it with the labels. Everything else in the loop — the optimiser, the batches, the evaluation — carries over unchanged, because nothing in it ever depended on the target being a label.

Twenty epochs of Adam at $10^{-3}$, batches of 128, 12,000 images: a CPU is enough.

What the loss sees

Rows two and three, PCA and the linear autoencoder, are the same reconstruction. Row five is what two numbers buy.

What the loss cannot see

Squared error on pixels is a distance between two arrays. It has no idea which pixels matter.

  • It rewards blur. The average of a class is close, in pixel distance, to every member of the class. A model short of capacity reconstructs the average and is scored well for it.
  • It is blind to a shift. Move a sharp edge one pixel and the error is large; smear it over three pixels and the error is smaller. The sharper reconstruction is the worse one, by this loss.
  • It measures pixels, not garments. A missing button costs nothing; a slightly different grey over the whole sleeve costs a lot.
Failure condition — a loss that rewards the average Reconstruction error falling is not the same as reconstructions improving. Look at them. A code chosen by the loss alone is a code tuned to reproduce the common, and the common is what you already knew.

Similar items: nearest neighbours, and how they are scored

def precision_at_10(Z):            # Z: one row per catalogue image
    Zq = Z[q]                        # 1,000 fixed queries
    D2 = (Zq**2).sum(1)[:, None] - 2 * Zq @ Z.T + (Z**2).sum(1)[None, :]
    D2[np.arange(len(q)), q] = np.inf          # not your own neighbour
    nn10 = np.argsort(D2, axis=1)[:, :10]
    return (y_test[nn10] == y_test[q][:, None]).mean()
  • Catalogue: the 10,000 test images; queries: 1,000 of them, each searching the other 9,999
  • $\lVert a - b\rVert^2 = \lVert a\rVert^2 - 2a\cdot b + \lVert b\rVert^2$: one matrix product instead of a loop over queries
  • Precision at ten: of the ten returned, the fraction of the query’s class. The label is read here and nowhere else.

The denoising autoencoder: the idea

Give the network a noisy image, and score it on how close its output is to the clean one.

  • When. The images you will process are noisy: phone photos, scans, low light
  • Why. A plain autoencoder reproduces the noise along with the garment. One trained noisy-in, clean-out has learned to remove it
  • When not. Clean images: there it is slightly worse than the plain one (the measured slide shows by how much)
  • Also, not measured here. It stops the network copying even when the code is wide

It needs only clean images: the noise is added by us, during training.

The denoising autoencoder: one line changes

for xb in batches(X_fit):
    xin  = (xb + 0.3 * torch.randn_like(xb)).clamp(0, 1)   # noisy input
    opt.zero_grad()
    loss = F.mse_loss(net(xin), xb)                        # clean target
    loss.backward(); opt.step()
  • Line 2 adds random noise to every pixel (pixels run from 0 to 1; the noise has standard deviation 0.3), then clips the result back to between 0 and 1
  • Line 4 feeds the noisy image in, and compares the output with the clean image xb
  • The noise is drawn anew every time an image is used. If each image always carried the same noise, the network could learn that noise by heart

Same network, same loop: the plain autoencoder is this loop with line 2 removed.

The variational autoencoder

beyond the syllabus, for context

The autoencoders so far give one code per image and nothing in between: decode a point between two codes and there is no reason the output is a garment. The variational autoencoder makes the encoder output a distribution — a mean and a spread for each number of the code — samples a code from it, and adds a second term to the loss that keeps every such distribution close to a standard normal.

That term is a regulariser on the code — the third row of the bottleneck table — and it fills the code space: a code drawn from a standard normal decodes to something plausible, which makes the decoder a generator.

The reparametrisation trick

beyond the syllabus, for context

A sampled code breaks the chain rule of Lecture 8: there is no derivative of a random draw with respect to the parameters that chose its distribution. The repair moves the randomness outside the graph:

  • Draw standard normal noise first, and treat it as an input
  • The code is then the mean plus the spread times the noise: an ordinary computation on the encoder’s outputs
  • Reverse mode differentiates through the mean and the spread as through any layer; the draw is never differentiated

Not examined. It is here because every generative model you will meet after this course contains this move.

Design exercise · in the manner of an ML system-design interview

The task: “see similar” on a fashion marketplace

The brief An online fashion marketplace sells garments listed by thousands of independent brands and shops. The product is its shopping app; the feature is a “see similar” strip under every item page, and a camera search that finds catalogue items like a photo the shopper took. The users are shoppers; the customers are the sellers, who pay a commission on every sale. The business measures the strip’s click-through, the conversion it adds, and the return rate of what it sells.
  • Given: millions of seller photographs with an unreliable category field, the shoppers’ click and purchase logs, the sellers’ stock and price feeds
  • Consumers of the output: the strip, and the camera search
  • Regulators: data protection, for the shoppers’ photographs; consumer protection and brand owners, for what “similar” may show

Eight steps follow, each with its pitfall; the model at the centre is today’s code, learned from the photographs alone.

Step 1 — Frame it honestly: a ranking, scored as one

  • The output is a ranked list of catalogue items for one query image; the metric is precision at the strip’s length on held-out items, read beside its anchor: the same strip filled from the query’s category at random
  • The label for scoring comes from what shoppers did — items viewed or bought in the same session — cleaned of the strip’s own clicks; the seller’s category field is a weak second source
  • The baseline before any model: the same category, in stock, most popular first
Pitfall Reporting the reconstruction error. It is the training signal, and the shopper never sees it: a code can reconstruct every photograph beautifully and return the wrong garments. Score the ranking the product shows, and report it against the anchor, or the first number will say nothing about the feature.

Step 2 — The photographs are not as alike as the dataset’s

PitfallWhat happensWhat to do
Studio, not garmentsellers shoot on different backgrounds, at different sizes, on or off a model; a code learned from the pixels learns the studio, and the strip returns the same seller’s other itemscrop to the garment, resize, normalise the background before anything is fitted; check the strip for seller clumping
Shoppers’ photographsa camera-search image is personal data, and is nothing like a studio shotencode on the device or discard after encoding; never keep the photo; train the encoder with camera-style augmentations
Duplicatesthe same garment listed by four sellers, and in six colourslink variants to one item before splitting, or the split leaks

Write down what one “item” is before the first fit. Every later number is a number about that unit.

Step 3 — Split by item, and by seller

  • Hold out whole items — every photograph and variant of them — and hold out whole sellers for a second check: the feature has to work for a shop that joined this morning
  • Choose the code size, the distance and the ranking rules on the validation items; read the test items once
Pitfall A random split over photographs puts the red and the blue of one dress on both sides. The nearest neighbour of a held-out photo is then its own item in another colour, precision looks superb, and the number says nothing about a garment the catalogue has never seen. Split on the item identifier from step 2, and keep a seller-level split beside it.

Step 4 — Learn the code from the catalogue, and size it by the ranking

  • Train the autoencoder on the whole catalogue of standardised photographs — no labels needed, so every listing counts, and a convolutional encoder once the photographs are real-sized
  • Read the code from the encoder alone; sweep its size and pick the smallest that holds the validation precision — the cost table says why smallest
  • Denoising and augmentation as the regulariser: the same garment, shifted, in another colour, on another background, must land on the same code
Pitfall Choosing the code size by reconstruction error. It falls at every increase, forever; the ranking metric flattens early and the index cost does not. A code sized by the loss is a code sized by the wrong question, and the bill for it is paid on every query.

Step 5 — The index: codes stored once, searched in milliseconds

  • Encode every catalogue item once, when it is listed, and store the code beside it; the query is encoded at request time and compared against the stored codes, never against the photographs
  • Exact search is a matrix product at a hundred thousand items; at millions, an approximate-neighbour index trades a little recall for a hundred-fold speed, and that recall is measured, not assumed
  • Normalise the codes to unit length and compare by cosine, so that a bright photograph is not far from a dark one of the same dress
Pitfall A distance nobody chose. The code’s coordinates are in a basis the optimiser landed on, and one coordinate with a large range dominates the Euclidean distance. Normalise, or whiten against the validation set, and check that the strip’s neighbours do not all share one bright background.

Step 6 — Similarity is one feature of the ranking, not the ranking

  • The strip ranks the nearest hundred by a second model that sees similarity, stock, size availability, price band, the seller’s return rate and the shopper’s history — a table, and a boosted ensemble on it
  • Business rules sit on top: in stock only, the shopper’s size, nothing from a seller under review
Pitfall — the look-alike under a brand’s page Visual similarity is blind to who made the garment. Under a luxury brand’s listing the strip shows the imitations that look most like it, the brand — a paying customer — sees its page selling look-alikes, and the counterfeit complaints land with the regulator. Brand and seller constraints belong in the ranking layer, and the similarity model must never be the last word.

Step 7 — Release, monitor, retrain

  • Release behind an A/B test on live traffic, read on the strip’s click-through, the conversion it adds and the return rate of what it sells, with the sellers’ exposure held fair across both arms
  • Monitor the distribution of codes as the catalogue turns over with the seasons; retrain on a schedule and re-encode the whole catalogue in one atomic swap of the index
  • Keep a randomised slot in the strip, so that the clicks the next model trains on are not only the ones this model chose
Pitfall Two encoders in one index. A retrained encoder puts the same garment at a different code, so an index holding codes from both versions compares numbers that no longer mean the same thing, and the strip fills with garments that are near nothing. Version the encoder with the index, and never serve a query from one against codes from the other.

Step 8 — Ship it: pipeline and pitfalls

Standardised photographs, variants linked into items → split by item and seller → autoencoder, code sized on validation precision → normalised codes, versioned index → ranking with business rules → A/B test → retrain, re-encode, monitor.

What we did

  1. Trained a network with no labels: compress to a code, reconstruct, and make the bottleneck the constraint — a regulariser, because without it the identity is reachable
  2. Measured the baseline: a linear autoencoder lands where PCA is, the best flat compression
  3. Built the non-linear one: a sixth below PCA at $d = 32$, and above it at $d = 128$, because a trained approximation is not an exact optimum
  4. Read the code as a representation: 32 numbers retrieve and cluster as well as 784 pixels, and no better, at a twenty-fourfold saving — the loss never saw a pair
  5. Denoising: noisy images in, clean images out. It removes the noise a plain autoencoder reproduces, and costs a little on clean images
  6. Designed a marketplace’s “see similar” feature in eight steps — a ranking metric against its anchor, standardised photographs, a split by item, a code sized by precision, a normalised versioned index, business rules above similarity, an A/B test — each named for the pitfall it avoids

Solutions — Lecture 10

1. A random forest ranks a census sampling weight first by impurity importance, yet shuffling that column on…

It is computed on the training rows, where a fully grown forest fits even noise; and a column with a distinct value per row offers a split almost anywhere, so some split on it always cleans a small node.

  • It measures how much the trees used the column to fit, not how much predictions on new rows depend on it
  • On the census data the weight is first by impurity and eleventh of twelve by permutation on held-out rows

2. The partial dependence of a model's probability on age rises from 0.015 at 20 to 0.270 at 50. Say what the…

It averages the ICE curves, one per applicant with age varied and the rest kept. It hides interactions — the married rise from 0.030 to 0.490, everyone else from 0.003 to 0.092 — so the average describes nobody.

  • Draw the ICE curves, coloured by the suspected interaction, beside the average
  • The average sits between the two groups, at a slope no applicant has

Solutions — Lecture 10 (2)

3. Define the Shapley value $\phi_i$ of feature $i$ for one prediction, given a value function $v$ over…

$\phi_i = \sum_{S\subseteq N\setminus\{i\}} \frac{|S|!\,(M-|S|-1)!}{M!}\bigl(v(S\cup\{i\})-v(S)\bigr)$, the marginal contribution of $i$ averaged over all $M!$ orders of the features. In one order the contributions telescope to $v(N)-v(\varnothing)$; averaging a constant over the orders leaves it unchanged.

  • Exactly $|S|!\,(M-|S|-1)!$ orders put the features of $S$ before $i$ and the rest after it
  • In every order the marginal contributions telescope to $v(N)-v(\varnothing)$

4. A classifier is applied to two groups whose base rates differ, and at its threshold the two groups have the…

Counting the true positives two ways gives $\text{TPR}\cdot p = \text{selected}\cdot\text{PPV}$ in each group. With equal selection rates and equal PPV the right-hand sides are equal, so $\text{TPR}_1 p_1 = \text{TPR}_2 p_2$, and equal TPRs would force $p_1 = p_2$.

  • The true positives are $\text{TPR}\cdot p\,n$ as a share of those with $Y=1$, and $\text{PPV}\cdot\text{selected}\cdot n$ as a share of those selected
  • Any two of the three criteria fix the third by the ratio of the base rates

Solutions — Lecture 10 (3)

5. A bank removes the applicant's sex from its model's inputs and reports that the model is therefore fair.…

The other answers predict sex — on the census data the twelve remaining answers predict it at an AUC of 0.9327 — so the model can use it through proxies; and without the attribute nobody can measure whether outcomes differ by sex. Keep the attribute under separate access for the audit, and measure the criteria per group.

  • Removing a column removes neither its correlates nor what the model learned through them: the household relationship alone names the sex of every married applicant
  • Fairness is a property of outcomes per group, which can only be measured with the group recorded
