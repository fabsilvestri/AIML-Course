The organising principle

Chapters never introduce themselves.

Every method enters this course at the moment an application breaks without it. You will not be shown regularisation and then given a problem for it. You will overfit something you built, measure it, and want the fix.

Each application spans two lectures.

A · Build

15 min — the problem, the data, the stakeholder.

15 min — choose a metric and commit to a target number, in writing, on paper.

60 min — build the simplest thing that runs. Everyone leaves with a number they are pleased with.

B · Break → Fix

20 min — the mathematical thread.

20 min — diagnose why that number was wrong.

35 min — the method that repairs it.

15 min — re-measure, and red-team a peer's notebook.

The number committed at the end of every Build lecture is what makes the following Fix lecture land: you predicted, you were wrong, and now you want to know why.

Working method

AI-assisted development. You will not type most of the code in this course — you will specify, read, test, debug and verify it.

#StepWho
1Specify — the input, the output, the constraint, the checkyou
2Generate — and then stop, before running anythingthe assistant
3Read — as a reviewer, not as an authoryou
4Test — against a case whose answer you already knowyou
5Verify — that the number means what it appears to meanyou

Steps 3–5 are the course. Step 2 is the part that is free.

Why the emphasis on verification

Machine learning fails silently. A bug in a training loop does not crash — it returns a plausible number:

  • A scaler fitted before the split leaks the test set into training. Great score, broken system.
  • A missing model.eval() leaves dropout active during evaluation.
  • A missing optimizer.zero_grad() accumulates gradients with no error.
  • A metric averaged per batch rather than over the set is wrong by construction.
  • Accuracy on an imbalanced set reports 90% for a model that predicts one class.

Every one of these runs. Every one produces a number. Each is diagnosed in a lecture, on code we wrote ourselves.

The notebooks are ours. The textbook supplies the syllabus, not the code. No notebook from the author, or from any other third party, is used in this course. Every notebook is written during the lecture, from a specification — and every lecture includes at least one worked assistant failure: an under-specified prompt, the plausible code it returns, the review question that catches it, and the corrected specification.

Four rules

  1. You may not submit code you cannot explain line by line. I will ask.
  2. Every number needs a baseline. A metric with nothing to compare it to is decoration.
  3. Every model needs an ablation. Remove a component; show the number moves.
  4. Report the failure cases. A system with no known failure mode has not been tested.

Prerequisites

Short version: the mathematics of a third-year BSc in Mathematics of Artificial Intelligence, and enough Python to read code critically. If you are missing something, none of it takes long to fix — and everything below is a pointer, not a reading list to complete before the first lecture.

A note on scope. Everything taught in this course comes from Chapters 1–16 of the textbook. The material on this page is the opposite: it is what the course assumes you already have, so the resources here necessarily point outside the book. None of it is examinable in its own right.

Test yourself in ten minutes

These are not warm-up exercises. Each one is a thing you will actually be asked to do, in the lecture where it appears. Try them before deciding you need to revise anything.

  1. $\mathbf{X}$ is $m \times n$ and $\boldsymbol\theta$ is $n \times 1$. What is the shape of $\mathbf{X}\boldsymbol\theta$, and why is $\mathbf{X}^{\mathsf T}\mathbf{X}$ square?

    Lecture 2, first ten minutes.

  2. Differentiate $\lVert\mathbf{X}\boldsymbol\theta - y\rVert^2$ with respect to $\boldsymbol\theta$. Then say what has to be true of the Hessian for the stationary point to be a minimum.

    Lecture 2. This is the derivation, not a preliminary to it.

  3. When is $\mathbf{X}^{\mathsf T}\mathbf{X}$ not invertible? Answer in terms of the columns of $\mathbf{X}$.

    Lecture 2, and again in Lecture 6 when ridge repairs it.

  4. $A$ and $B$ each have variance $\sigma^2$ and correlation $\rho$. What is $\operatorname{Var}\!\left(\tfrac{A+B}{2}\right)$?

    Lecture 8. This single calculation explains bagging, random forests and extra-trees.

  5. What does a 95% confidence interval mean — and what does it not mean?

    Lecture 2, on the final test score.

  6. a has shape (100, 3), b has shape (3,). What does a - b compute, and what shape comes out? Now b has shape (100,) — what happens?

    Every lecture. Silent broadcasting is silent.

  7. Given a DataFrame df, select the rows where df["x"] > 5, keeping only columns "a" and "b". Then count how many values in "a" are missing.

    Lecture 1, within the first twenty minutes of the build.

  8. Read this traceback out loud and say which line of your code caused it, and why:
    ValueError: Input X contains NaN.

    Lecture 1. You will cause this one personally.

Could you do six or more? You are ready; skip the rest of this page. Fewer? Find the matching row below. Nothing here needs more than a few evenings, and none of it needs to be finished before Lecture 1 — the items are listed in the order the course first needs them.

What you explicitly do not need

Prior machine learning

Helpful, not assumed. The course starts from a problem and a dataset on the first day and builds everything from there.

Deep learning or GPU experience

Parts II–IV assume nothing beyond what Parts I–II established. Neural networks arrive in Lecture 11, because a classical model has run out of room.

Software engineering

No production systems, no deployment infrastructure, no build tooling. Notebooks throughout.

Fluent typing

You will not type most of the code. You will specify, read, test, debug and verify it — and that is the part being examined.

Assessment

Two components, in the usual order: a written examination, and an oral examination taken only by candidates who pass it.

Written examination

Two hours, closed book, no formula sheet. Three parts: the mathematical threads, a code review on paper, and diagnosis from evidence.

A pass is required to sit the oral, and does not carry to another session.

Oral examination

Twenty to twenty-five minutes, on any topic from the course — the twelve applications, the twelve mathematical threads, and the working method.

No notes, no computer.

Marks and sessions Each part must be passed independently: at least 18/30 on the written and at least 18/30 on the oral. The final mark is their average, weighted 50/50. A strong written mark therefore cannot compensate for a failing oral — you have to be able to explain your own work.

Both are taken in the same session: a written pass does not carry forward, so a candidate who does not sit or does not pass the oral resits the written as well.

Can a course this applied really have a written examination?

Yes — and this course is better suited to one than most applied courses, for a specific reason.

The competence being built here is not typing. It is judgement about whether a result can be trusted, and that judgement is exercised by reading: reading code you did not write, reading a metric, reading a curve. Reading is paper-native. A written examination tests it more directly than a lab does — at a keyboard a student can arrive at the right answer by running things until they look right, whereas on paper they have to actually know.

Three rules keep it honest.

  1. No question tests API recall. In a course where you deliberately do not type the code, asking for the arguments of train_test_split would be incoherent. Syntax errors in handwritten code cost nothing; logic errors cost everything.
  2. No question is answerable by reciting a definition. Every one requires applying it to a stated situation.
  3. The paper states what it needs. There is no formula sheet, and none is required: any definition or standard result a question depends on is printed in the question itself. What you are expected to supply is the reasoning, never the recall.

This is why closed book costs you nothing here. Each of the twelve threads is a derivation you have performed — a result you can rebuild in three lines is not a result you need to have memorised.

What a written examination cannot see is whether you can make something work at all. That is exactly what the oral is for.

The written examination

The three parts below are weighted within the paper. The paper as a whole is half the final mark.

PartWhat it asksWeight
of the paper		Time
A · The mathematical threads Derive, state, apply. The twelve objects developed at the top of each Fix lecture — the normal equation, the bias–variance decomposition, variance reduction by averaging, reverse-mode differentiation, cross-entropy, and the rest. 40% ~48 min
B · Code review on paper A printed notebook excerpt with a reported number. Find every path by which the result could be untrustworthy, cite the line, and say what the honest procedure would be. This is the red-team exercise, sat individually and under exam conditions. 35% ~42 min
C · Diagnosis from evidence Plots and tables — learning curves, per-fold scores, a confusion matrix, a precision/recall curve. Name the pathology, prescribe the fix, and say which way the number will move. 25% ~30 min

Three specimen questions

One from each part, at the intended level and scale — each is calibrated to the time budget above.

Part A — derive, then apply

Two regressors each have variance $\sigma^2$ and are correlated with coefficient $\rho$.

  1. Show that the variance of their average is $\frac{\sigma^{2}(1+\rho)}{2}$.
  2. Bagging and a random forest differ in one respect. State it, and say which term in your expression it attacks.
  3. An ensemble of one hundred identical trees has $\rho = 1$. What does your expression predict, and is that the right answer?

Part B — code review on paper

best = None
for a in [0.01, 0.1, 1, 10, 100]:
    m = Ridge(alpha=a).fit(X_train, y_train)
    s = root_mean_squared_error(y_test, m.predict(X_test))
    if best is None or s < best[1]:
        best = (a, s)

print(f"best alpha={best[0]}, test RMSE={best[1]:,.0f}")
  1. This program never creates a validation set. Which object is doing that job?
  2. As an estimate of the model’s error on new data, the printed RMSE is (i) too optimistic, (ii) too pessimistic, or (iii) neither. Choose one and give the reason in a sentence.
  3. Rewrite the program so the printed number is honest. Two statements is enough.
  4. In expectation over repeated train/test splits, is the honest number higher or lower than the printed one? Is that guaranteed on any single split?

Every part has one determinate answer — the test set; (i); a cross-validated search on the training data, scored once on the test set; higher, and no. Nothing here rewards a well-phrased opinion, and none of it can be answered without knowing what a validation set is for.

Part C — diagnosis from evidence

Two teams report the following for the same dataset.

TeamTraining RMSE10-fold CV RMSE
A$0$68,779
B$68,233$68,316
  1. Name each pathology.
  2. Which model is more useful? Explain why that is not the same question as which is better fitted.
  3. One of these is helped by collecting more training data and the other is not. Which, and why?

The oral examination

The whole syllabus is examinable. An oral usually opens with a topic drawn from the course, and then asks you to ground it in something you built.

On the course

  • “Take any Fix lecture. What broke, and why did the repair work?”
  • “Why does averaging trees reduce variance — and why does averaging a hundred identical trees not?”
  • “When would you prefer MAE to RMSE, and what would you tell the stakeholder?”
  • “Why is precision not monotone in the threshold?”
  • “Where does this course’s scope end, and what did we deliberately not cover?”

On what you built

  • “Pick one application. What metric did you choose, what number did you commit to, and what did you actually get?”
  • “Where did you first meet leakage in your own work, and how did you detect it?”
  • “Describe a component you could remove from one of your systems. What would happen to the metric, and why?”
  • “Name a decision you made that you would now make differently, and say what changed your mind.”

Nothing is collected and nothing is graded as an artefact. The twelve applications are examinable as experience: you are expected to be able to account for what you built and why, without the code in front of you.

Rule one is checked here. You may not present work you cannot explain — and the oral is where that is verified. It applies to code an assistant wrote for you exactly as it applies to code you typed.

Note what is absent: there are no marks for a notebook that runs. Evidence earns marks.
