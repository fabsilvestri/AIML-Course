Mathematical thread 1

Least squares and
the normal equation

20 minutes

The question

You called LinearRegression().fit().

What did it actually compute — and when does that computation fail?

Why you need the answer The failure condition is exactly the warning from the previous lecture about engineering features as weighted sums.

The linear model

$$\hat{y} \;=\; \theta_0 + \theta_1 x_1 + \theta_2 x_2 + \dots + \theta_n x_n$$
  • $\hat{y}$ — the predicted value
  • $n$ — the number of features
  • $x_i$ — the $i$-th feature value
  • $\theta_j$ — the $j$-th model parameter, including the bias term $\theta_0$

A weighted sum of the input features, plus a constant called the bias or intercept term.

Vectorised form

$$\hat{y} \;=\; h_{\boldsymbol\theta}(\mathbf{x}) \;=\; \boldsymbol\theta \cdot \mathbf{x}$$

where $\mathbf{x}$ contains $x_0$ through $x_n$ with $x_0 \equiv 1$, so the dot product reproduces the bias term.

In machine learning, vectors are usually column vectors. With that convention the prediction is $\boldsymbol\theta^{\intercal}\mathbf{x}$ — the same quantity, written as a single-cell matrix rather than a scalar.

What “fit” means

Training the model means setting $\boldsymbol\theta$ so the model best fits the training set. To do that we need a measure of how badly it fits.

$$\mathrm{MSE}(\mathbf{X}, y, h_{\boldsymbol\theta}) \;=\; \frac{1}{m}\sum_{i=1}^{m}\left(\boldsymbol\theta^{\intercal}\mathbf{x}^{(i)} - y^{(i)}\right)^{2}$$

Mean squared error of a linear hypothesis

Why minimise MSE and not RMSE?

Because $\sqrt{\cdot}$ is strictly increasing on $[0,\infty)$:

$$\arg\min_{\boldsymbol\theta} \sqrt{f(\boldsymbol\theta)} \;=\; \arg\min_{\boldsymbol\theta} f(\boldsymbol\theta)$$

Same minimiser, simpler algebra.

Learning algorithms often optimise a different function during training than the one used to evaluate the final model — because it is easier to optimise, or because it carries extra terms needed only during training.

In matrix form

Stack the instances as rows of $\mathbf{X}$ and the labels into $y$:

$$\mathrm{MSE}(\boldsymbol\theta) \;=\; \frac{1}{m}\,\lVert \mathbf{X}\boldsymbol\theta - y \rVert_2^{\,2}$$

We are minimising a squared Euclidean norm. That is a geometric statement, and it is the whole content of this thread.

Differentiate and set to zero

$$\nabla_{\boldsymbol\theta}\,\mathrm{MSE}(\boldsymbol\theta) \;=\; \frac{2}{m}\,\mathbf{X}^{\intercal}\!\left(\mathbf{X}\boldsymbol\theta - y\right)$$

Setting the gradient to zero at the minimiser $\hat{\boldsymbol\theta}$:

$$\mathbf{X}^{\intercal}\!\left(\mathbf{X}\hat{\boldsymbol\theta} - y\right) \;=\; \mathbf{0}$$

A stationary point. Is it a minimum?

Why that stationary point is the minimum

The Hessian of the MSE is

$$\nabla^{2}_{\boldsymbol\theta}\,\mathrm{MSE} \;=\; \frac{2}{m}\,\mathbf{X}^{\intercal}\mathbf{X}$$

For any vector $\mathbf{v}$, $\;\mathbf{v}^{\intercal}\mathbf{X}^{\intercal}\mathbf{X}\mathbf{v} = \lVert \mathbf{X}\mathbf{v}\rVert_2^2 \ge 0$, so the Hessian is positive semi-definite and the MSE is convex.

A convex function has no local minima — only a global one. Any stationary point is it.

This is also why gradient descent, in Lecture 6, is guaranteed to find the same answer.

The normal equation

Rearranging $\mathbf{X}^{\intercal}\mathbf{X}\hat{\boldsymbol\theta} = \mathbf{X}^{\intercal}y$:

$$\hat{\boldsymbol\theta} \;=\; \left(\mathbf{X}^{\intercal}\mathbf{X}\right)^{-1}\mathbf{X}^{\intercal}\,y$$

A closed-form solution — no iteration required

A closed-form equation is composed only of a finite number of constants, variables and standard operations. No infinite sums, no limits, no integrals.

Read it geometrically

Look again at the stationarity condition:

$$\mathbf{X}^{\intercal}\underbrace{\left(\mathbf{X}\hat{\boldsymbol\theta} - y\right)}_{\text{residual } \mathbf{r}} \;=\; \mathbf{0}$$

Every column of $\mathbf{X}$ is orthogonal to the residual.

Least squares is orthogonal projection

  • $\mathbf{X}\boldsymbol\theta$ ranges over the column space of $\mathbf{X}$ as $\boldsymbol\theta$ varies
  • Minimising $\lVert \mathbf{X}\boldsymbol\theta - y\rVert_2$ finds the point of that subspace closest to $y$
  • The closest point of a subspace to a vector is its orthogonal projection
Fitting a linear model is projecting the label vector onto the span of the features. The residual is what the features cannot reach.

Verify it on our own data

If the geometry is right, the residual must be orthogonal to every column of $\mathbf{X}$ — so $\mathbf{X}^{\intercal}\mathbf{r}$ should be numerically zero.


residual = X_b @ theta_best - y
print(np.abs(X_b.T @ residual).max())        # ~1e-9, i.e. zero

Not exactly zero: floating-point arithmetic. But nine orders of magnitude below the scale of the data.

A cheap, decisive check that your solver did what the mathematics says it should.

Compute it directly


import numpy as np
from sklearn.preprocessing import add_dummy_feature

X_b = add_dummy_feature(X)              # add x0 = 1 to each instance
theta_best = np.linalg.inv(X_b.T @ X_b) @ X_b.T @ y

The @ operator is matrix multiplication. PyTorch, TensorFlow and JAX all support it; pure Python lists do not.

And compare


>>> lin_reg = LinearRegression()
>>> lin_reg.fit(X, y)
>>> lin_reg.intercept_, lin_reg.coef_
(array([3.69084138]), array([[3.32960458]]))

Identical, to floating-point precision.

Note that Scikit-Learn separates the bias term (intercept_) from the feature weights (coef_).

When does this break?

The equation requires $\left(\mathbf{X}^{\intercal}\mathbf{X}\right)^{-1}$ to exist.

$\mathbf{X}^{\intercal}\mathbf{X}$ is $(n{+}1)\times(n{+}1)$. It is invertible if and only if it has full rank — equivalently, if and only if $\mathbf{X}$ has linearly independent columns.

Two ways to lose that.

Failure 1 · More features than instances

If $m < n$, then $\operatorname{rank}(\mathbf{X}) \le m < n+1$, so $\mathbf{X}^{\intercal}\mathbf{X}$ is singular.

Infinitely many parameter vectors fit the data exactly. The problem is not that there is no solution — it is that there are too many.

Common in genomics, text, and any wide-feature setting.

Failure 2 · Collinear features

If one column is a linear combination of others, the columns are dependent and $\mathbf{X}^{\intercal}\mathbf{X}$ is singular again.

The previous lecture’s warning, explained “When creating new combined features, avoid simple weighted sums of existing features.”

A weighted sum of existing columns is a linear combination. You would be manufacturing the singularity yourself.
This is the payoff of the callback. Pause here.

Near-singular is also a problem

Exact collinearity is rare; near collinearity is common.

  • $\mathbf{X}^{\intercal}\mathbf{X}$ is invertible but ill-conditioned
  • Tiny changes in the training set produce large changes in $\hat{\boldsymbol\theta}$
  • The model becomes numerically unstable

In Lecture 6 we will repair this with ridge regression, which adds $\alpha\mathbf{A}$ and makes the matrix invertible for every $\alpha > 0$.

What Scikit-Learn actually does

It does not invert anything. It computes

$$\hat{\boldsymbol\theta} \;=\; \mathbf{X}^{+}\,y$$

where $\mathbf{X}^{+}$ is the pseudoinverse — specifically the Moore–Penrose inverse.


np.linalg.pinv(X_b) @ y                  # same result

Computed by SVD

Singular value decomposition factors the training matrix as

$$\mathbf{X} \;=\; \mathbf{U}\,\boldsymbol\Sigma\,\mathbf{V}^{\intercal} \qquad\Longrightarrow\qquad \mathbf{X}^{+} \;=\; \mathbf{V}\,\boldsymbol\Sigma^{+}\mathbf{U}^{\intercal}$$

To build $\boldsymbol\Sigma^{+}$: take $\boldsymbol\Sigma$, set to zero every value below a tiny threshold, replace the remaining values by their reciprocals, and transpose.

The pseudoinverse is always defined, even when the inverse is not.

What it costs

MethodIn $n$ (features)In $m$ (instances)
Normal equation$O(n^{2.4})$ to $O(n^{3})$$O(m)$
SVD (Scikit-Learn)$O(n^{2})$$O(m)$
  • Double the features with the normal equation → roughly 5 to 8 times slower
  • Double the features with SVD → roughly 4 times slower
  • Both are linear in the number of instances — they handle large training sets well, provided the data fits in memory

Both become very slow when $n$ grows large — say 100,000 features. That is what gradient descent is for.

Thread 1 · Summary

  • Fitting a linear model minimises $\lVert\mathbf{X}\boldsymbol\theta - y\rVert_2^2$
  • The minimiser satisfies $\mathbf{X}^{\intercal}(\mathbf{X}\hat{\boldsymbol\theta}-y)=\mathbf{0}$: the residual is orthogonal to every feature
  • Hence $\hat{\boldsymbol\theta} = (\mathbf{X}^{\intercal}\mathbf{X})^{-1}\mathbf{X}^{\intercal}y$, when the inverse exists
  • It fails to exist when $m < n$ or when features are collinear
  • The SVD-based pseudoinverse is always defined and cheaper

Examinable: derive the normal equation; state and justify the invertibility condition.

Part two

Diagnose

20 minutes · why a tree scored zero

The suspect

0.0

A decision tree made no error at all on 16,512 districts.

Two hypotheses. Only one of them is flattering.

Hypothesis 1 · The model is perfect

Housing prices would have to be an exact deterministic function of eight census attributes.

  • Two identical districts would always have identical median prices
  • No measurement noise anywhere in a census
  • No influence from anything not in our eight columns

Reject.

Hypothesis 2 · The model memorised

A decision tree left unconstrained keeps splitting until every leaf is pure.

With enough depth it can isolate every single training district into its own leaf. Then predicting the training set is a lookup, and a lookup has zero error.

This is overfitting: excellent on the training data, useless on anything else.

Why trees are especially prone to it

Decision trees make very few assumptions about the data. Left unconstrained, the tree structure adapts itself to the training data — fitting it very closely, most likely overfitting it.

Such a model is called nonparametric: not because it has no parameters, but because the number of parameters is not fixed before training, so the structure is free to follow the data.

But overfitting is not the bug

Overfitting is a property of the model.

The bug is that we could not see it.

The cardinal error We measured the RMSE on the same data the model was trained on.

Training error tells you almost nothing

  • It measures how well the model reproduces what it has already seen
  • The goal is performance on new instances
  • Low training error with high generalisation error is the definition of overfitting

Linear regression’s $68,973 was also a training number. It happens to be roughly honest — but only because the model is too rigid to memorise anything.

“Then use the test set”

No.

We are still choosing between models and tuning them. If we consult the test set now, we will select whatever suits it, and our estimate of generalisation error becomes optimistic.

The test set is used once, at the very end, to estimate the generalisation error of a system we have already committed to.

A second bug, which we avoided by luck

Consider this extremely common pattern:


# WRONG — do not do this
scaler = StandardScaler()
housing_scaled = scaler.fit_transform(housing_full)      # all the data
train_set, test_set = train_test_split(housing_scaled)   # then split

The scaler saw the test set. Its mean and standard deviation encode information from data the model must not know about.

Data leakage

Definition Information from outside the training set influences the model. The reported score improves. The deployed system does not.

Leakage is the single most common way a machine learning result becomes fiction. It never raises an exception.

Our code in the previous lecture escaped it — not because we were careful, but because we happened to put the scaler inside a pipeline. Let us make that deliberate.

The rule, stated once

Never violate this Fit every transformer on the training set only. Never call fit() or fit_transform() on the validation set, the test set, or new data. Once fitted, you may transform() anything.

This applies to imputers, scalers, encoders, dimensionality reduction — everything that learns anything from data.

Diagnosis

NumberVerdict
Linear regression — $68,973roughly honest; the model underfits
Decision tree — 0.0meaningless: memorised, measured on itself
Random forest — $17,551meaningless for the same reason

We need a way to estimate generalisation error without touching the test set.

Fix 1 · Hold out a validation set

Split the training set again: a smaller training set, and a validation set (also called the development set, or dev set).

  1. Train candidate models on the reduced training set
  2. Select the one that performs best on the validation set
  3. Retrain that model on the full training set
  4. Evaluate once on the test set

Holdout validation has a tension

Validation set too small

Evaluations are imprecise; you may select a suboptimal model by chance.

Validation set too large

The remaining training set is much smaller than the full one — like selecting a sprinter to run a marathon.

Solution: many small validation sets, used in rotation.

Fix 2 · $k$-fold cross-validation

Split the training set into $k$ non-overlapping folds. Train and evaluate $k$ times, holding out a different fold each time.

$$\text{score} \;=\; \frac{1}{k}\sum_{j=1}^{k} \text{RMSE}\!\left(\text{model trained without fold } j,\ \text{fold } j\right)$$

Cost: you train the model $k$ times.

In code


from sklearn.model_selection import cross_val_score

tree_rmses = -cross_val_score(tree_reg, housing, housing_labels,
                              scoring="neg_root_mean_squared_error", cv=10)
Why the minus sign Scikit-Learn’s cross-validation expects a utility function (greater is better), not a cost function. The scorer is the negative RMSE, so flip the sign back.

  • Linear regression — the two columns nearly agree. It is not overfitting; it is underfitting
  • Decision tree — $0 against $66,574. Severe overfitting, and barely better than the linear model
  • Random forest — $17,551 against $47,038. Still overfitting, but by far the best honest score

Fixes for overfitting: simplify the model, constrain it, or obtain more training data.

Why does averaging trees help?

A random forest trains many decision trees on random subsets of the features, then averages their predictions.

If the underlying models are diverse, their errors are not strongly correlated, so averaging smooths the errors out, reduces overfitting, and improves overall performance.

In Lecture 8 we quantify exactly this — thread 4 gives the variance of an average of correlated predictors.

Fix 3 · Pipelines make leakage structurally impossible


full_pipeline = Pipeline([
    ("preprocessing", preprocessing),
    ("random_forest", RandomForestRegressor(random_state=42)),
])

When cross_val_score holds out fold $j$, the entire pipeline — imputer, encoder, scaler, model — is fitted on the other folds only.

The transformers never see the held-out fold. Leakage cannot occur by accident.

Fix 4 · Tune, instead of guessing


from sklearn.model_selection import GridSearchCV

param_grid = [
    {'preprocessing__geo__n_clusters': [5, 8, 10],
     'random_forest__max_features': [4, 6, 8]},
    {'preprocessing__geo__n_clusters': [10, 15],
     'random_forest__max_features': [6, 8, 10]},
]
grid_search = GridSearchCV(full_pipeline, param_grid, cv=3,
                           scoring='neg_root_mean_squared_error')
grid_search.fit(housing, housing_labels)

Double underscores address any hyperparameter of any estimator, however deeply nested.

Note what we just tuned

preprocessing__geo__n_clusters is not a model hyperparameter. It belongs to a preprocessing step.

Wrapping preprocessing in a pipeline lets you tune preprocessing hyperparameters together with model hyperparameters — which matters, because they interact.

Grid search result


>>> grid_search.best_params_
{'preprocessing__geo__n_clusters': 15, 'random_forest__max_features': 6}

Best cross-validated RMSE: $43,590, improved from $47,038.

Read the boundary 15 was the largest value we tried for n_clusters. The optimum may lie outside the grid. Search again with higher values.

Randomised search is usually better


from sklearn.model_selection import RandomizedSearchCV
from scipy.stats import randint

param_distribs = {'preprocessing__geo__n_clusters': randint(low=3, high=50),
                  'random_forest__max_features': randint(low=2, high=20)}

rnd_search = RandomizedSearchCV(full_pipeline, param_distributions=param_distribs,
                                n_iter=10, cv=3,
                                scoring='neg_root_mean_squared_error',
                                random_state=42)

Why randomised wins

  • Run it for 1,000 iterations and it explores 1,000 distinct values of each continuous hyperparameter — a grid explores only the few you listed
  • Add a hyperparameter that turns out not to matter: a grid multiplies the runtime, a random search does not
  • Six hyperparameters with ten values each means a million grid fits. Randomised search runs for however long you allow

Spending the compute budget better

HalvingGridSearchCV and HalvingRandomSearchCV run a tournament:

  1. Generate many candidate configurations
  2. Evaluate them all with limited resources — typically a small slice of the training set
  3. Only the best candidates advance, with more resources each round
  4. The finalists are evaluated at full resource

Same search space, considerably less compute — or a much larger space for the same compute.

A third way to improve the system

Combine the models that perform best. A group will often beat the best individual member — just as a random forest beats the trees it is built from.

This works best when the individual models make different kinds of errors. Averaging correlated mistakes achieves nothing.

We return to this properly in Lecture 8, where thread 4 makes “different kinds of errors” precise.

Also check fairness

A model should work well not only on average, but across categories of district — rural or urban, rich or poor, northern or southern.

Build subsets of the validation set per category and analyse performance on each. If the model performs poorly on a whole category, it should not be deployed for that category — it may do more harm than good.

Finally: the test set


X_test = strat_test_set.drop("median_house_value", axis=1)
y_test = strat_test_set["median_house_value"].copy()

final_predictions = final_model.predict(X_test)

$41,446

Note we predict on the test set. We never fit anything on it.

How precise is that estimate?


from scipy import stats

def rmse(squared_errors):
    return np.sqrt(np.mean(squared_errors))

squared_errors = (final_predictions - y_test) ** 2
boot_result = stats.bootstrap([squared_errors], rmse,
                              confidence_level=0.95, random_state=42)
rmse_lower, rmse_upper = boot_result.confidence_interval

95% interval: $39,521 – $43,702.

A point estimate alone may not be enough to justify a launch — especially if the improvement over the incumbent is small.

One last temptation

Resist it If you tuned a lot, test performance is usually slightly worse than cross-validated performance, because the system was fine-tuned to the validation data. When that happens you must not tweak hyperparameters to make the test number look better.

Those improvements would not generalise. You would simply be overfitting the test set instead.

Red-team exercise

Swap notebooks with the team beside you. You have ten minutes.

  1. Find any place where a transformer is fitted outside the training set
  2. Find any metric computed on data the model was trained on
  3. Find any hyperparameter chosen by looking at the test set
  4. Check whether the split was stratified — and on what

Report what you found, not what you would have done differently.

Leakage checklist — keep this

  • Was every transformer fitted after the split, on training data only?
  • Is preprocessing inside the pipeline passed to cross-validation?
  • Was the reported metric computed on held-out data?
  • Was the test set touched more than once?
  • Were hyperparameters selected using validation data, not test data?
  • Does any feature encode information unavailable at prediction time?

Six questions. They will catch most of what goes wrong in this course and in your projects.

Can the assistant red-team for you?

Partly — and only if you ask it as an adversary, not as an author.

“Is this code correct?”
Invites agreement. You will usually get it.
“This notebook reports RMSE $49{,}682$. Assume that number is optimistic. List every path by which test-set information could have reached the training procedure, and cite the line.”

Give it the failure to look for, and a number to disbelieve. Generic review requests return generic praise.

Moving the check upstream

Everything diagnosed today was preventable at specification time. Keep this as a standing constraint in every request:

Standing constraint “Split before anything is fitted. All preprocessing lives inside a Pipeline passed to cross-validation. Nothing derived from the test set may appear in the training path. Fixed random seed. Print the fold scores, not just the mean.”

A specification is cheaper than a diagnosis. This one would have saved us the first forty minutes of this lecture.

Ask them to paste this into their own notes now. It recurs, extended, in every application from here on.

If you were to ship this


import joblib

joblib.dump(final_model, "my_california_housing_model.pkl")

Save every model you experiment with, along with its cross-validation scores and its predictions on the validation set. It lets you compare scores across model types and compare the kinds of errors they make.

Deployment is not the end. You need monitoring, because performance decays quietly through data drift.

Presenting the solution

What separates great data scientists from good ones is not the model. It is the communication of it.

  • Concise reports; visualise the key insights
  • Tailor the message: technical for peers, high-level for stakeholders
  • Give one memorable statement — here: “median income is the number one predictor of housing prices”
  • State what worked, what did not, what you assumed, and where the system is limited

And make it reproducible

  • Code accessible to the team, with a structured README
  • Clear notebooks: code, explanation and results together
  • A requirements.txt or environment.yml pinning exact library versions — or a container image
  • Seeds set for every random generator; every other source of variability removed

This is graded. A result nobody else can reproduce is not a result.
