The question

You called clf.fit().

It computed 266,610 partial derivatives, on every batch, 20 times over. How?

Why you need the answer Because the cost of that computation is what decides whether training a network is possible at all — and the reason it is possible is a property of the direction in which the chain rule is applied.

The chain rule, as a product of Jacobians

A network is a composition. Write the loss as

$$L \;=\; f_3\!\left(f_2\!\left(f_1(\boldsymbol\theta)\right)\right) \qquad\Longrightarrow\qquad \frac{\partial L}{\partial \boldsymbol\theta} \;=\; J_3\,J_2\,J_1$$

where $J_i$ is the Jacobian of $f_i$ evaluated at the point the forward pass reached. Every layer contributes one factor.

Matrix multiplication is associative.

So the product can be bracketed from either end. $(J_3 J_2)\,J_1$ starts at the output — reverse mode. $J_3\,(J_2 J_1)$ starts at the parameters — forward mode. Same number; very different cost.

Reverse mode · propagate an adjoint

Pick a direction in output space — for a scalar loss there is only one, and it is 1. Carry $\bar{u} = \partial L / \partial u$ backwards:

$$\bar{u}_{\text{in}} \;=\; \bar{u}_{\text{out}}\, \frac{\partial f}{\partial u_{\text{in}}}$$
  • One sweep gives the derivative of one output with respect to every input
  • The forward values must be kept, because the Jacobians are evaluated at them — that is the memory cost

Forward mode, bracketed from the other end, gets one input direction per sweep, so a gradient over $n$ parameters costs $n$ sweeps. Reverse mode costs one sweep per output — and a loss has exactly one.

The whole derivation, in one picture

One sweep forward fills in the values, one sweep back every derivative — and $x$, used twice, sums its two edges.

Animation

So: what is backpropagation?

In one sentence Reverse-mode automatic differentiation, applied to a neural network, with the seed set to 1 at the loss.
  • It is not specific to neural networks
  • It is not an approximation
  • It is not gradient descent — it supplies the gradient that descent then uses

The 1986 paper’s contribution was noticing that this was cheap enough to be practical, not inventing the chain rule.

The accuracy is not the bug

MLPClassifier, refitted on this lecture’s 12,000 images: 87.38% validation accuracy against a 10.0% baseline is a real result.

Nothing here was measured dishonestly. The split was clean, the validation set was separate, the test set was touched once.

The bug is that you cannot do anything else.

The accelerator’s lead grows with the arithmetic per batch

At the smallest width the two devices nearly tie. From there the ratio climbs, because each batch carries more arithmetic to cover the cost of dispatching it.

Why requires_grad builds a graph

It does not compute a derivative. It says record what happens to me.

  • Every operation on a recording tensor creates a node holding the operation and its inputs
  • The graph is built during the forward pass, by running it — there is no separate compilation step
  • It is rebuilt from scratch on every batch, which is why a Python if inside forward just works

That is the forward sweep from this lecture’s mathematics block, with the graph written down as it goes so the reverse sweep has something to walk.

You can look at the graph


>>> u = torch.tensor(2.0, requires_grad=True)
>>> v = torch.tensor(3.0, requires_grad=True)
>>> q = u * v + torch.sin(u)
>>> r = q ** 2
>>> r.grad_fn
<PowBackward0 object at 0x1291a4b50>
>>> r.grad_fn.next_functions
((<AddBackward0 object at 0x1291a4be0>, 0),)

Those are the nodes in the diagram, by name. Walking next_functions to the leaves is the reverse sweep.

And you can turn it off


with torch.no_grad():
    preds = model(X_val)          # no graph is built
  • Evaluation needs no derivatives, so recording them wastes memory proportional to the size of the batch
  • On a large validation set the difference is the difference between fitting on the GPU and not

Forgetting no_grad is slow and memory-hungry, but it is not a correctness bug. The two bugs that follow are.

The training loop

model = build_model().to(device)
opt   = torch.optim.Adam(model.parameters(), lr=1e-3)
lossf = nn.CrossEntropyLoss()

for epoch in range(EPOCHS):
    model.train()
    for xb, yb in train_loader:
        opt.zero_grad()                       # 1
        out  = model(xb)                      # 2
        loss = lossf(out, yb)                 # 3
        loss.backward()                       # 4
        opt.step()                            # 5

Five lines. There is no hidden machinery: this is the whole of what fit() was doing.

train() and eval()

Some layers behave differently in the two phases. Two of them matter in this course:

LayerIn train()In eval()
Dropoutzeroes a random fraction of unitspasses everything through
Batch normalisationuses this batch’s statisticsuses the running averages

The module defaults to training mode. Build a model, never call eval(), and every evaluation you make is of a randomly crippled network.

Batch normalisation arrives in Lecture 9; the same failure applies to it and is harder to see, because it does not fluctuate.

Failure condition — the module is still in training mode nn.Module defaults to training mode, so dropout stays active and batch normalisation keeps updating its running statistics through every evaluation. Nothing raises. The number is simply of a different model than the one you meant to score.

A custom module

class Sorter(nn.Module):
    def __init__(self, widths=(300, 100), n_in=784, n_out=10):
        super().__init__()
        sizes = (n_in,) + tuple(widths)
        self.blocks = nn.ModuleList(
            nn.Linear(a, b) for a, b in zip(sizes, sizes[1:]))
        self.head = nn.Linear(sizes[-1], n_out)

    def forward(self, x):
        for blk in self.blocks:
            x = torch.relu(blk(x))
        return self.head(x)

super().__init__() before anything else: it creates the registry the layers are recorded in, and assigning a layer before it raises AttributeError: cannot assign module before Module.__init__() call. Everything after that — .to(device), .parameters(), state_dict() — comes for free.

Searching the hyperparameters properly

The previous lecture tuned by hand: ten points, one axis at a time. Optuna proposes a configuration, trains it briefly, scores it, and lets a sampler choose the next from what it has learned.


def objective(trial):
    lr   = trial.suggest_float("lr", 1e-4, 1e-2, log=True)
    drop = trial.suggest_float("dropout", 0.0, 0.5, step=0.1)
    return validation_accuracy(train(lr=lr, dropout=drop, epochs=4))

study = optuna.create_study(direction="maximize")
study.optimize(objective, n_trials=8)
Not examinable Optuna is not in the book. It is here because it is what you will actually use, and because it makes the point that hand tuning was never a search.

Saving the model


torch.save(model.state_dict(), "sorter.pt")          # the tensors

fresh = build_model().to(device)
fresh.load_state_dict(torch.load("sorter.pt", weights_only=True))

The tensors are 1041 KB — 266,610 float32 numbers, and this is their size, not the file’s. The notebook prints what the file actually weighs, and it is a little more: state_dict is written as a zip archive, so the names and the container are in there too.

What not to do torch.save(model, ...) pickles the object, and unpickling it needs your class definition at the same import path. Next term, when the file has moved, the checkpoint will not load.

And check the reload


assert accuracy(model, X_test, y_test) == accuracy(fresh, X_test, y_test)

accuracy counts hits over the whole set, in eval() mode, under no_grad. Not “it looks about the same”: a reloaded network is either the same function or it is not, and the difference is one assertion.

The usual cause of failure is loading a state_dict into a model built with different widths. PyTorch raises for that — but only if you did not pass strict=False to silence it.

Design exercise · in the manner of an ML system-design interview

The task: the training pipeline behind a ride-hailing app’s arrival-time model

The brief A ride-hailing app shows every rider, at booking, how many minutes away the driver is — a network fitted on past trips, which several engineers retrain every week. Too early and the rider cancels; too late and the booking is lost. The pipeline takes a configuration and produces a checkpoint, a validation error and a record of both, so a colleague can reproduce the number and a reviewer release it.
  • Given: the trip log — request, pickup, driver position at dispatch, traffic, arrival — the model class, and the loop written out
  • Scale: millions of trips a week; a model that fits on one machine; many runs a day
  • Consumers of the output: the engineer who retrains, the reviewer who releases, the service behind every booking

Nine steps follow, each with the pitfall that catches a first attempt and what to do about it. The model at the centre is today’s: the five-line loop, owned, and three bugs that never raise.

Step 1 — Frame it: a number nobody can reproduce is not a release

  • A run outputs three things: the checkpoint, the mean absolute error in minutes counted over the whole validation set, and the configuration and seed behind them
  • The baselines: the rule the app shipped first — distance at the city’s average speed — and last week’s checkpoint, scored the same way on the same split
  • The reference: the same network under the convenience wrapper, whose loss curve the loop must overlay
Pitfall Every failure in this lecture ran to completion and printed a plausible number; a gate that looks for exceptions passes all of them. Judge runs on behaviour: the same configuration twice gives the same curve, the loop’s sits on the wrapper’s, and the new checkpoint beats last week’s on the same split, or it is not released.

Step 2 — Dataset, DataLoader, and a split written to disk

  • A Dataset answers how many, and give me trip $i$; a DataLoader shuffles and batches, and the interface does not change when a week of trips stops fitting in memory
  • Split once per retrain, by time — the latest days are validation — and save the indices; every engineer’s validation set is the same file
  • Shuffle the training loader with a seeded Generator; the validation loader is not shuffled at all
Pitfall shuffle=True with no generator: every run sees the batches in a different order, and two engineers comparing a tenth of a minute are comparing shuffles. A split redone from a different seed on another machine moves trips between training and validation, and the number is of a different experiment. One split file, one generator, both named in the configuration.

Step 3 — The loop, written out, and the first bug that never raises

  • model.train(), then per batch: zero_grad, forward, loss, backward, step — five lines, every one a place to print, clip, log or stop
  • The loss is the one the product asked for, the absolute error in minutes, which the wrapper had no argument for; one loop function for the team, reviewed once, the per-epoch loss logged
Pitfall — the missing zero_grad() backward() adds to p.grad, so without the clearing line every step uses the sum of all gradients so far. It runs, the loss falls for a while, and the model is little better than the rule it replaced, and nothing raises. It is caught by reading the loop — which is why the team has one — and by the overlay against the wrapper’s curve.

Step 4 — One evaluate() for everyone: eval(), no_grad, counted

RuleWithout it
model.eval() firstdropout stays on and the error is of a randomly crippled network
under torch.no_grad()a graph is recorded for nothing: slow and memory-hungry, though not wrong
count over the whole seta plain mean of per-batch errors weights the short last batch as a full one
run it twicean error that wobbles between identical calls has a layer still in training mode
Pitfall Each engineer writes their own evaluation and each omits a different line. The missing eval() cost under a point today and the per-batch mean a small fraction of one; neither shows in the number, and either decides a release. One function, called by the loop, the search, the reload check and the gate.

Step 5 — Seeds: the same run twice, then several runs before a claim

  • Seed everything that draws a random number — the weights, the loader’s generator, the split — and record the seed with the configuration; the same seed on the same machine must give the same curve
  • A difference between two configurations is a claim only when it is larger than the spread between seeds of one configuration: run a few seeds and report mean and spread
Pitfall An engineer reports a gain of a few seconds of error from a new dropout rate, measured on one seed against a colleague’s one seed. The seeds alone move the number by as much, and the release meeting argues about a change that did nothing. Reproduce first, repeat second, and only then compare.

Step 6 — A hyperparameter search with a budget

  • Hand tuning was never a search. An Optuna objective proposes a configuration, trains it for a few epochs, scores it with the team’s evaluate() on validation, and the sampler chooses the next
  • Fix the number of trials and the epochs per trial in advance, so the search fits the week’s retrain, and log every trial, failed ones too
  • Retrain the winner with the full budget, then read the test split — the last day, held back — once
Pitfall The best trial’s validation error is reported as the model’s. It is the minimum of many draws on the set it was chosen on, so it is optimistic; and it was earned on a short budget, so the ranking is a measurement of that budget. The search chooses a configuration, not a number: the number comes from the retrained winner, on trips it never saw.

Step 7 — Save the tensors, rebuild the model, and check the reload

  • torch.save(model.state_dict(), path) — the tensors and their names, nothing else — beside the configuration that built it, so the service can call build_model(config) without the training code
  • Reload with weights_only=True into a fresh model and assert that evaluate() returns exactly the same error — in the pipeline, and in the service at load
Pitfall torch.save(model, path) pickles the object, and unpickling needs the class at the same import path — the service has another, and the checkpoint fails at release. strict=False loads a state_dict into a model of different widths in silence, layers missing, and every rider gets an estimate nobody validated. A reloaded network is either the same function or it is not: one assertion.

Step 8 — In production: the weekly release, the rollout, and the clock

  • A checkpoint that passes the gate goes to a share of bookings in one city against last week’s, read on error against real arrivals and on cancellations — the A/B test; last week’s file is the rollback, its engineer on call
  • Wall-clock is a measurement of one machine: time pairs of runs that differ in one thing — framework on one CPU, device with one code — and record machine, device and batch size
Pitfall “PyTorch on the GPU is several times faster” — one number for two changes, read on one laptop, in a hardware ticket. Taken one at a time, the device alone nearly ties at the smallest width. A second is not a figure: it is a reading from a named machine, stored as one.

  1. Derived reverse-mode differentiation: the chain rule is a product of Jacobians, and bracketed from the output end it costs one sweep per output
  2. Concluded that training — many parameters, one scalar loss — leaves reverse mode as the only viable choice; that is what backpropagation is
  3. Found that the wrapper costs control, not accuracy, and that an accelerator’s lead grows with the arithmetic per batch
  4. Wrote the training loop — tensors, requires_grad, the graph, backward(), the optimiser step — and got the same model back
  5. Met three bugs that raise nothing: a missing zero_grad(), a missing model.eval(), a metric averaged per batch
  6. Added DataLoader, a custom Module, an Optuna search, and a checkpoint checked by assertion
  7. Solutions — Lecture 7

1. A multilayer perceptron with the activation removed is written as $W_3W_2W_1x$. State what function class it…

Only linear maps — the product of matrices is a matrix.

  • Composition of linear maps is linear, whatever the depth
  • The nonlinearity is what makes an extra layer a new function rather than a re-parameterisation

2. Give the parameter count of a dense layer from $m$ inputs to $n$ units, and evaluate it for the first layer…

$mn + n$; here $784 \times 300 + 300 = 235{,}500$.

  • One weight per input-output pair, plus one bias per unit
  • The first layer of an image network usually dominates the count, because $m$ is the pixel count

Solutions — Lecture 7 (2)

3. A ten-class classifier for mutually exclusive classes is built with ten sigmoid output units and binary…

It is the multilabel row. Mutually exclusive classes are the multiclass row: ten units, softmax, cross-entropy.

  • Ten sigmoids ask ten independent yes/no questions, and their outputs need not sum to 1
  • Softmax couples the outputs into one ten-way question, and cross-entropy with a one-hot target is minus the log probability of the true class

4. Fashion-MNIST is exactly balanced across ten classes. State the trivial baseline’s accuracy, and why…

10%. With equal class sizes and equal costs, accuracy is not dominated by one class.

  • The majority-class predictor scores the largest class share, which is one tenth
  • Lecture 3's objection to accuracy was imbalance, and it does not apply

Solutions — Lecture 7 (3)

5. An architecture sweep finds the best hidden-layer size on this dataset. State what that result does and does…

Very little. It holds for this task at the training-set size you swept at. In the lecture the order survived a move from 6,000 to 12,000 images, but that is a measurement on this corpus, not a guarantee: only a re-run on all the data says whether a subset’s ranking was real.

  • A deeper network needs more data to pay for its extra parameters, so a ranking measured on a fraction of the data can change on the rest
  • It is a measurement of one sweep at one size, not a rule. Reporting it as a general recommendation is the error
